# Модель исполнения

## Назначение

Определяет, как ведётся работа в слое [03-execution/](../03-execution): как заводятся задачи,
как они claim'ятся, выполняются и закрываются. Модель намеренно простая: одна задача — единица
работы. Нет goal/slice-иерархии, нет многошаговой admission-церемонии.

## Единица работы — задача

Задача (`TASK-*`) — минимальный bounded шаг работы. У задачи есть:

- запись в [task-registry.edn](../03-execution/02-tasks/task-registry.edn);
- файл `TASK-XXX.md` в [02-tasks/](../03-execution/02-tasks);
- ссылка на canonical `doc_id`, к которому относится работа;
- `owned_modules` — список путей/модулей, которые задача меняет (для безопасной параллельной работы);
- `status`: `ready`, `in_progress`, `done`, `superseded`, `cancelled`.

ID задачи зарезервирован только когда есть и запись в реестре, и файл.

## Жизненный цикл задачи

1. **ready** — задача описана, ждёт исполнителя.
2. **claim** — агент берёт задачу: `bb work-claim --task TASK-XXX`. Создаётся лок в
   [05-locks/](../03-execution/05-locks) (локальный, не коммитится). Claim проверяет, что
   `owned_modules` не пересекаются с другими активными claim'ами.
3. **in_progress** — агент выполняет работу в пределах scope и owned_modules.
4. **verification** — прогон лестницы верификации из `engineering-profile.md`.
5. **done** — `bb work-done --task TASK-XXX`: лок снимается, статус переводится в `done`,
   обновляются state snapshot, файл задачи и журнал сессии.

## Параллельная работа

Несколько агентов могут работать параллельно, если их `owned_modules` не пересекаются. Это
единственная защита от конфликтов — никаких распределённых локов не требуется, потому что всё
на одном хосте.

Git-механика параллельной изоляции описана в [git-workflow.md](git-workflow.md): один агент
работает в `dev`, несколько — каждый в своём локальном worktree.

## Граница

- Операционные артефакты обязаны ссылаться на canonical `doc_id`.
- Если execution и canonical расходятся — побеждает canonical.
- Закрытие задачи требует пройденной верификации и обновлённого состояния.
- Прямое редактирование статуса задачи в обход `bb work-done` не приветствуется: состояние
  должно обновляться согласованно (реестр + файл + state + сессия).
