# Foundation Contract

## Назначение

Определяет, как устроен слой [02-foundation/](../02-foundation) и какие факты в нём обязаны
быть. Это контракт построения foundation для любого проекта, а не правда конкретного проекта.

## Что такое foundation

[02-foundation/](../02-foundation) — каноническая правда конкретного проекта. Отвечает на
вопросы:

- что истинно про этот проект;
- что должен делать продукт;
- на каком языке/стеке и какими командами проект восстанавливается и запускается.

**Reconstructability (обязательно).** Foundation должен быть достаточным, чтобы новый агент по
текущим canonical docs восстановил и запустил рабочий проект в объявленном стеке — без опоры
на скрытую переписку. Это правило stack-agnostic: конкретный язык и команды фиксируются в
`engineering-profile.md`, feature docs фиксируют поведение без противоречий.

Foundation **не** место для общих правил фреймворка и переиспользуемых workflow — это слой
[01-standards/](.).

## Структура

### 01-product — продуктовая правда

- `product-intent.md` (`PROD-INTENT`) — зачем продукт существует, для кого, какую проблему решает.
- `product-scope.md` (`PROD-SCOPE`) — что входит в продукт и что явно вне его границ.

### 02-project — проектная правда

- `engineering-profile.md` (`PROJ-ENGINEERING`) — стек, инструменты, и команды
  **bootstrap / run / test / build**, достаточные для восстановления рабочего проекта.
  Это критичный документ для reconstructability.
- `glossary.md` (`PROJ-GLOSSARY`) — операционный глоссарий терминов проекта, чтобы человек,
  агент и код понимали слова одинаково.

### 03-features — поведение функций

Папка на функцию. Каждая описывает каноническое поведение: назначение, сценарии, acceptance
criteria, edge cases. Минимум один feature-документ на каждую реализованную функцию.

### 04-decisions — архитектурные решения

ADR на каждое нетривиальное архитектурное решение: контекст, решение, последствия, границы.

## Обязательный минимум

Чтобы проект считался корректно описанным:

- `product-intent.md` и `product-scope.md`;
- `engineering-profile.md` с рабочими командами run/test/build;
- `glossary.md` (может быть пустым на старте);
- по одному feature-документу на каждую реализованную функцию;
- ADR на каждое нетривиальное архитектурное решение.

## Граница стека

Язык и стек продукта — любые, фиксируются в `engineering-profile.md`. Фреймворк не навязывает
конкретный язык. Babashka/Clojure применяются только внутри самого фреймворка (его
автоматизация), если это удобно, и не являются требованием к продукту.
